# Private intake workflow tabletop

Walkthrough of the proposed [Phase 1 service contract](03_PHASE_1_BUILD_BRIEF.md), using fictional records. Each row follows the expected record, operator action and consumer message from the initial event to resolution. The resulting changes are in the candidate build brief. This exercise reviewed the specification. Runtime acceptance tests and participant sessions are pending.

| Case | Fictional event sequence | Required result | Specification change |
|---|---|---|---|
| W01 Lost submission response | Consumer saves a description-only draft with an unknown date and chooses Submit. The first response is lost after the service commits. They retry. | The case stays in intake with the same receipt and one screening task. The date remains unknown. The consumer sees “Report received” once the service confirms the receipt. | Bind the receipt to the submitted draft revision. Replay it for a duplicate of that revision. Direct a different revision to the current case and its correction path. |
| W02 Scan result arrives late | Consumer submits while attachment version A is pending, then replaces it with B. The scan of A completes first. | The report is received. B remains pending. The viewer can open B only after its own checks. If B fails, the consumer can replace it or continue with the description. | Key scan decisions to the exact object version and route failed scans to an evidence task. Keep intake receipt, attachment readiness and reviewer decision independent. |
| W03 Two reviewers claim one task | Two staff members see the same unassigned intake. The first claim commits. The other then attempts to claim it. | The first reviewer receives the assignment. The second sees “Already assigned” and the refreshed queue, with routing metadata only. Reassignment changes access for subsequent requests. | Tie the queue count and list to the same filter. Serve protected evidence through a session-checked route and re-evaluate assignment on each new request. Previously received copies require separate handling. |
| W04 Clean image contains unrelated personal details | Malware checks complete successfully. The assigned reviewer notices an unrelated identity document in the image. | Restrict the version and create a privacy review task. Offer the consumer a route to replace it or continue with the description. Record the decision and any required hold without copying the sensitive content into the task. | Distinguish scan safety from content restriction. Restriction also applies to ordinary evidence previews and exports while the privacy lead resolves scope. |
| W05 Export overlaps deletion | A consumer's export is generated. An approved deletion decision later covers some records in it. The consumer returns to the export link. | The stale export becomes unavailable. Explain the change and reissue an export containing only permitted records if appropriate. The deletion status reflects what was removed and what remains held. | Recheck export access at retrieval and invalidate affected exports when scope changes. Reconcile temporary exports alongside primary objects before reporting completion. |
| W06 Restore after deletion | The team restores a database and object backup from before an approved deletion. | Keep consumer and staff access closed during reconciliation. Apply deletion records through the chosen recovery cutoff, verify object inventory and hold scope, and reopen only when the restore lead confirms the result. | Define how the restore process will recover deletion records created after the backup snapshot. A snapshot alone cannot supply that history. Document the recovery source and failure stop condition. |

The two highest-impact changes are the session check on each protected download and a way to recover deletion decisions made after a backup snapshot. Both need runtime evidence before live use. For W02 and W04, test the difference between “report received”, “attachment checking” and “attachment restricted” with users so the messages describe the case state accurately.
